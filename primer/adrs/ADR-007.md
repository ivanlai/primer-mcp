## Parent Epic
[[EP-001]]

## Context
The ticket models rejected any unrecognised frontmatter key, and the CLAUDE.md snippet written into every adopter's project told them to create and update tickets only through the tools. Together those made the store brittle and closed. Removing one field, `blocks`, required rewriting all 32 tickets in this repo, and a single stale key would block every tool call against a store. That in turn demanded a version stamp, a version gate, a migration path, and an error message that could not give correct advice because two different causes produced the same failure. Each fix exposed the next. Meanwhile the same rule was quietly broken twice in one session, correctly both times.

## Decision
Split tolerance from enforcement along the data/workflow line. Data is tolerant: models accept unknown keys and write them back untouched, so a field can be added or removed without breaking any store and an older build never silently drops what a newer one wrote. Workflow stays gated: the Epic -> ADR -> Story -> Task order and two-phase completion are enforced and not bypassable. Hand-editing by user or agent is explicitly allowed for anything except a status the workflow owns — `verified` and `done` are reached through the tools or not at all. A schema version is recorded in config.yaml but never enforced, purely because a stamp cannot be added retroactively.

## Alternatives Considered
- Keep rejecting unknown keys and build the migration path — rejected: every field removal becomes a breaking change needing a migration engine, a version gate and a store that refuses to open until fixed. That rigidity is what makes the systems this tool reacts against unpleasant, and it buys only typo detection
- Ignore unknown keys rather than preserving them — rejected: worst of both. An older build reading a newer store would silently delete fields it did not understand, losing data with no error
- Keep tools-only authoring and rely on the gates — rejected: the store is markdown in the user's own git repo, and `editable without the tool` is a stated reason that format was chosen. Claiming exclusive write access to a user's files is the lock-in this project avoids
- Report unrecognised keys as a warning on read — deferred, not rejected: worth roughly two lines inside get_ticket when it is built, but it is code for a problem not yet encountered

## Consequences
A mistyped key is inert rather than loud: `blockedby: [TK-001]` is preserved and does nothing, with no warning. Judged acceptable because the tools are the interface and do not mistype. Removed fields also linger as cruft, since nothing strips them. In exchange, schema change stops being an event — the `blocks` removal would have needed no migration at all — and validation now fails only on genuine corruption, which makes `restore it from git` correct advice instead of ambiguous. This deleted more code than it added: the version gate and its tests went with it. The tolerance has a hard limit: it covers unknown fields, not malformed YAML. A stray colon in a hand-edited list item fails in frontmatter.loads before pydantic runs, and takes the whole store with it — proven within minutes of adopting this policy. `git checkout` is the remedy, which is what the load error already advises.

## Superseded

The data-tolerance half of this decision stands. The workflow-enforcement half — "Workflow stays gated ... enforced and not bypassable" — is superseded by [[ADR-008]], which replaces hard gates with soft nudges. The AI advises the planning-first flow rather than blocking operations that skip steps.
