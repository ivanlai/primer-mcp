## Parent Epic
[[EP-001]]

## Context
update_ticket can set status to todo, in-progress or blocked. Applied to an already-verified task that would silently undo the two-phase gate and strand the parent story at `done`, breaking the derived-status cascade. Jira permits reopening freely, so the divergence needs justification.

## Decision
update_ticket rejects any status change on a ticket already in a terminal state: task `verified`, spike `done`, story or epic `done`. `completed` is intermediate, not terminal, so completed -> in-progress is allowed — the graceful path when complete_task proves premature. The dividing line is verified_evidence: before it exists backing up is free; after it exists backing up contradicts a recorded fact.

## Alternatives Considered
- Allow reopening via a plain status edit, as Jira does — rejected: verified_evidence records test output that was true when written; reopening would leave a field asserting the tests passed on a task now claiming they did not
- Recompute parents after every update_ticket call instead of guarding — rejected: a guard is cheaper than a second cascade path and states the intent directly

## Consequences
update_ticket can never change whether a parent's criteria are met, so it needs no cascade of its own. Reopening becomes a deliberate, recorded act — specified by the reopen_task story. A primer-mcp task is one session and ~3 files, closer to a commit than a bug report, so a follow-up task is usually the honest answer anyway.
