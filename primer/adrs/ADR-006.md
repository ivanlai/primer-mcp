## Parent Epic
[[EP-001]]

## Context
architecture.md specifies todo -> in-progress -> done for spikes, but no start_spike tool exists, so `in-progress` is unreachable for them. Separately, a spike exists to answer a question before committing to an approach, which invites an implicit rule that an open spike should block the tasks beside it.

## Decision
Treat spikes as todo -> done and amend the architecture doc to match. get_next_action offers complete_spike directly, quoting the timebox. An open spike does not implicitly gate sibling tasks; where a spike really must precede a task, express it with blocked_by on that task.

## Alternatives Considered
- Add a start_spike tool so the documented lifecycle becomes true — rejected for now: widens the query-and-graph-tools story past its four specced tools; worth its own small story if spike progress tracking is ever wanted
- Make an open spike block every task under the same story — rejected: a gate that appears in no document and surprises the agent, when blocked_by already expresses it explicitly

## Consequences
No hidden gates: every dependency in the system is either the Epic -> ADR -> Story -> Task hierarchy or an explicit blocked_by edge. Cost: the agent must remember to wire blocked_by when a spike genuinely blocks work, and a spike-only story becomes done when its spike closes.
