## Parent Story

## What to do
**What's gone wrong:** `</script>` is unescaped in export_graph (export.py:378) — ticket data is embedded into an inline script block via `json.dumps`, which leaves that literal verbatim. A ticket body that quotes HTML or code (e.g. discussing the export feature itself, or pasted test HTML) terminates the script element early: graph.html renders broken, and everything after the marker is parsed as author-controlled HTML — an injection vector as well as a rendering bug.

Fix is one line: `json.dumps(...).replace("</", "<\\/")`.

## Testable Outcome
A ticket whose body contains a literal script-closing tag exports to a graph.html that still parses and renders; the sequence appears escaped in the embedded JSON.

## Dependencies
- (none)

## Completion Notes
Added a `_safe_json(obj)` helper in `export.py` that wraps `json.dumps(obj).replace("</", "<\\/")`. Replaced all 5 `json.dumps()` calls in the `_HTML_TEMPLATE.format()` block with `_safe_json()` — this covers `nodes`, `edges`, `details`, `TYPE_COLOUR`, and `STATUS_BORDER`. The escape is applied uniformly rather than selectively because the cost is zero and it eliminates any future risk if constants were to include user-derived data.

Test in `TestScriptEscaping` creates a task whose body contains a literal `</script><h1>injected</h1>`, exports the graph, and asserts: (1) only the 2 template `</script>` tags remain raw, and (2) the escaped `<\/script>` form appears in the embedded JSON.
