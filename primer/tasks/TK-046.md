## Parent Story
[[ST-020]]

## What to do
Add edges from ADRs to stories in the project graph visualization.

The Story model already has an `adr_ids: list[str]` field (models.py:113). The graph export just doesn't draw edges for it.

## Steps

1. Backfill `adr_ids` on existing stories where an ADR informed the story's work
2. Add edges in `_build_graph_data` (export.py) from each ADR to stories that reference it via `adr_ids`
3. Use a distinct edge style (e.g. dotted purple) and add a legend entry
4. Regenerate graph and verify ADR-story edges appear
## Approach

ADRs currently connect only to their parent epic via hierarchy edges. A more useful view would also show which stories implement each ADR's decision.

This requires a new optional field on the Story model (e.g. `implements_adr: list[str]`) or, alternatively, a new optional field on the ADR model pointing at the stories it governs. The graph export would then draw additional edges between ADRs and their related stories.

## Considerations

- Which direction to store the relationship: on the story (pointing up at the ADR) or on the ADR (pointing down at stories). Storing on the story is more natural — a story is created after the ADR and knows which decision it implements.
- Edge styling: these edges are neither hierarchy (solid) nor dependency (dashed red). A third style (e.g. dashed purple or dotted) would distinguish them in the legend.
- Existing `blocked_by` is the only stored edge today (ADR-004). This would be a second kind of cross-reference — worth an ADR if the design decision is non-trivial.

## Testable Outcome
ADR nodes in the exported graph.html have edges connecting them to the stories that implement their decisions, with a distinct visual style and legend entry
